# Multi-child family admissions

## Parent experience
The public [Madrasah admission form](https://madrasah.attowfiqmasjid.org/apply/) accepts **one to six children in one submission**.

1. Enter each child's name, date of birth and gender. Use **Add another child** for siblings.
2. Enter guardian contact and household address **once**.
3. Complete separate Qur’an/Qaaidah, learning support and consent details for **each child**.
4. Review the family details and each child's information; submit only once.
5. Receive one family reference plus an individual application reference for every child; one acknowledgement email is attempted for the household.

Each child's application remains a separate `admissions` record and must be reviewed/accepted individually. Their progress, school class, fees and pupil numbers remain separate, while the existing guardian-linking process can associate siblings with the same parent account on acceptance.

## Server and privacy
- Public endpoint `POST /api/public/admissions` accepts legacy single-child JSON or new `children:[...]` with shared guardian fields.
- Limit: 1–6 children. All children are validated before insertion. Duplicate child identities within one form and invalid dates/consents are rejected.
- Cloudflare D1 `DB.batch()` inserts all siblings transactionally; no half-submitted family.
- Family submissions share a `family_application_id` generated by the server. Existing submissions have NULL.
- Parents get one summary acknowledgement containing names and per-child references but **no medical, allergy or support notes**. Email delivery is best effort after database commit.
- Public API does not expose an admissions register. Existing daily rate-limits and origin checks remain.
- Admin sees a family label and family reference in the admissions register. Individual decisions are unaffected.
- Form fields remain in memory only until explicit submission; no browser localStorage is used.

## Deployment and migration
**Apply migration 0016 before deploying the new Worker or exposing the new form.** Single-child public submissions to a new Worker will fail if `family_application_id` has not been added.

```powershell
cd C:\App\Madrasah-At-Towfiq-Portal\madrasah-at-towfiq-portal
git pull origin main
npm run test
npx wrangler@latest d1 time-travel info attowfiq_portal
# Check recovery/backup status. If D1 SQL export is supported, take a private backup outside the Git repo.
npx wrangler@latest d1 migrations apply attowfiq_portal --remote
npx wrangler@latest deploy
```

Then install the companion website update:
```powershell
cd C:\App\masjid-at-towfiq-website
git pull origin main
npx wrangler@latest deploy
```

## Smoke test
- Public form: submit one child as before; check its own reference and pending admin record.
- Public form: add two children; give them different learning/support needs and photo consents, and check one family email.
- Admin admissions: verify two separate new applications marked with the same family reference; approve one and leave the other pending.
- Verify there are no extra pupil accounts created until admissions are accepted.
- Use controlled test data only; don't submit actual children's health information as test material.

## Rollback
Revert the merge commit in the portal and companion website repositories, then redeploy. Leave the additive `family_application_id` column and index intact to preserve historical links. Do not roll back the whole D1 database and overwrite unrelated student changes.
